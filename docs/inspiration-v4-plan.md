# 灵感一现 V4：随手记录、第一性原理分析与可迁移存储

状态：设计提案。2026-11-14（Asia/Shanghai）。本文件不是已上线功能清单；提醒和数据迁移尚未执行。

## 1. 核心目标与验收

随手记录的成本保持低；收集后可以回到原文，识别待办、问题、观念与规划，看到依据和相关经验；采取实际行动后保留结果，逐步修订解释。离开 GPT 后仍可打开、检索、备份与迁移自己的数据。

验收标准：

- 一次输入可以拆成多项，并保留共同来源；原文与分析分别展示。
- 没有明确日期的任务不自动变成今天到期或逾期。确认的到期任务可以送达指定提醒渠道，完成或延期后对应提醒停止或更新。
- AI 转述不自动成为本人认同的观念；本人认同不自动成为经过验证的事实。
- 相同来源重复导入不产生重复任务；原文有变更时保留新版本和历史。
- 可以导出包含正文、任务、关系、分析版本、来源、附件与清单的可迁移包；关闭网络和退出 GPT 后仍能阅读。
- 修改单条任务只写入对应数据，不再整份读写所有个人知识。

## 3. 第一性原理分析层

统一路径：现象与原话 → 要实现的目标 → 已知事实与约束 → 隐含假设 → 候选机制 → 替代解释与反例 → 区分预测 → 最小验证行动 → 结果与修订。

“推测本质”在系统中表达为有情境、有边界的候选机制，不生成无证据的人格定论。对缺失来源、行业信息或现实观察明确标记未知。事实、解释和价值取舍分别保存。

每份分析至少包含：source_ids、phenomenon、goal、facts、constraints、assumptions、mechanisms、alternatives、counterevidence、discriminating_predictions、next_test、applicability、unknowns、analysis_version。

分析力度按内容选择：简单明确的待办只做执行规划；需要做取舍的规划或反复出现的现象才展开深度分析。停止条件是已能支撑当前决策并提出有效验证；不把反复问“为什么”当成完成了分析。

跨主题关联用“这两条在哪个条件下可能相通、证据是什么、哪里不能类推”描述。候选关联不是因果；关键词相似不是稳定规律。有关联依据的链接可以确认、纠正或停用。

成长记录至少区分表达变清楚、认知改变、真实行动改变和实际结果改变。聊天频率、卡片数量不直接作为成长成绩。

## 4. 随手记录模块

入口：一个混合内容输入框，支持文字粘贴、截图、文件与 WorkBuddy 结构化包。先保存原始内容再处理；日期、类型和标签可以后补。

建议入口名“随手记”，页面内五个视图：

1. 收件箱：新记录、待澄清字段、AI 拆分结果、来源。
2. 今日与近期：用户确认的日期任务、逾期、等待中、无日期队列；不擅自为无日期事项制造截止时间。
3. 观念与问题：核心观点、出处、本人是否认同、分析和反例、相关知识与模型。
4. 目标与计划：长期方向 → 阶段目标 → 项目 → 下一步行动，支持依赖与阻塞原因。
5. 回看与整理：需要复用的知识、到期假设、待补结果、已失效观点和版本历史。

信息可以同时进入多个视图；同一条原文不复制成几份互不更新的数据。保留原有四大领域与经验学习分支；“随手记”是输入与处理入口，不替代既有领域分类。

### 任务字段

id、source_ids、title、goal_id、project_id、next_action、acceptance_criteria、status、due_at、planned_at、timezone、deadline_source、reminder_policy、effort_estimate、dependencies、blocked_reason、created_at、updated_at、completed_at。

status：inbox / ready / doing / waiting / done / cancelled。取消和完成保留历史。due_at 是截止，planned_at 是计划执行时间；候选日期另放 suggested_schedule，不冒充本人承诺。

### 观念字段

id、original_text、source_ids、quoted_author、message_sender、authorship、adoption_status、evidence_status、interpretations、related_ids、applicability、counterexamples、review_at、versions。

authorship 至少支持 user_original / ai_quote / other_quote / unknown；adoption_status 与 evidence_status 相互独立。微信发送人是自己，不等于文本由自己原创。

## 5. 提醒与规划

- 第一版先让明确待办进入队列。每天建议聚焦少量行动，建议排期与本人已确认排期分开。
- 明确日期且已确认的事项才创建到期提醒。没有日期先留在待排期视图；不要将其误标为逾期。
- 提醒渠道应独立于 GPT。建议先用用户已有日历或飞书待办；实际连接、通知权限、时间和设备需要在实施时确定。
- 固定时点事项可以导出日历事件；静态日历导入不会自动回传完成状态，完整闭环需要独立的同步接口。
- 网站页面中的到期提示不等于手机推送。浏览器页面关闭后需后台调度与可送达渠道。
- 提醒任务引用 task_id；延期、完成、取消会更新/取消对应通知。保留 reminder_id、幂等键、送达状态、失败日志与重试次数，防止重复提醒。
- 固定任务提醒由确定性调度完成；AI 负责拆分和候选排期。不要让模型每次临时决定是否发送重要到期提醒。
- 本轮未提供截图事项的截止时间或提醒时段，因此没有为这些事项创建实际提醒。

## 6. 微信与 WorkBuddy 导入

优先尝试系统提供的“转发到其他应用 → WorkBuddy”入口；不同版本与设备以实际可见能力为准。可以用文字或截图补充，不能假设 WorkBuddy 可以自动遍历全部历史微信。

推荐链路：主动选择消息 → WorkBuddy 保留原文与来源并初步拆分 → 导出标准包 → 知识库预览导入 → 增量入库与关联。

WorkBuddy 作为采集与预处理器，数字分身负责持续关系、行动状态与历史。不得只保存一篇失去逐条来源的总结。

标准导入包：

- manifest.json：schema_version、batch_id、producer、created_at、timezone、文件清单、校验和。
- messages.jsonl：每行一条可追溯原消息；含原始编号或批次位置、作者、source_timestamp（不明为空）、captured_at、source_kind、原文与附件引用。
- analysis.jsonl：每行一条拆分结果；明确 source_ids、原文、类型、事实/推断/建议、待补信息、候选关系、分析版本；不替换消息原文。
- attachments/：截图、文件；原图不转成 Base64 塞进每条记录。
- README.md：人可以直接查看的批次摘要与覆盖缺失。

稳定 message_id 可用来源消息编号；取得不到时使用批次、位置与原文/附件哈希，不使用个人姓名或完整原文充当 URL。重复导入相同批次应幂等；不同日期相同文本也可能是独立事件，不跨场景强行去重。

若只能取得 WorkBuddy 总结，标记 secondary_summary，并降低来源覆盖程度，不将总结还原为逐字用户原话。截图 OCR 不确定的字保留待核验。

文件先导入预览：展示新增、重复、变更和待澄清事项；仅重复项不再生成待办，有变更保留版本。

当前我不能直接读取用户电脑上 WorkBuddy 的本地文件。第一阶段由用户上传导出包或放到明确连接并授权的资料位置。日后自动同步另建窄权限接口；不要向 WorkBuddy 暴露现有站点后台的全权限凭证。

## 7. 存储与平台独立性

推荐组合：结构化云数据库 + 原始文件对象存储 + 标准格式离线包。云端结构化数据是线上状态权威来源；原始来源文件不可变保存；本地 Markdown 和 SQLite 为一致性导出或阅读副本，不形成两个未经协调的主库。

| 内容 | 在线运行 | 本地可读与迁移 |
|---|---|---|
| 待办、日期、状态、目标、关系、版本索引 | 按条记录的 SQL 数据库 | SQLite 快照、JSONL/CSV |
| 核心观念、方法、复盘与分析 | 数据库正文或按文档存储 | Markdown，稳定 ID 与来源链接 |
| 微信原文、原对话、截图、文档和大附件 | 对象存储，数据库仅保存引用 | raw/、attachments/ 原文件 |
| 搜索索引和向量 | 可重建索引 | 索引清单，可重新生成 |
| 执行记录、提醒状态与历史事件 | 分页事件表/日志 | JSONL 日志与版本清单 |

技术选型：在当前 Worker 方案上，可先用 D1 存结构化记录、R2 存原始与附件；若要真正由用户控制，最终部署到用户自有云账号与域名，并补独立登录。SQLite 用于本地快照/导入工具，不把多个设备正在写入的 SQLite 文件直接扔网盘做实时同步。

飞书保留可编辑的人类文档入口。初期采用发布镜像和有版本的回读导入；不要同时开网页、飞书、Markdown 无规则双向写入。编辑内容必须回到同一条记录与修订流程。

离线包至少含 index.md、wiki/、raw/、attachments/、data/knowledge.sqlite、export/*.jsonl、manifest.json、schema.json、关系清单与附件校验和。普通文本编辑器能读 Markdown，SQLite 工具能查询任务关系；离线阅读无需 GPT 登录。可选打包离线只读 HTML 目录，便于直接双击浏览。

本地修改先作为新修订导入，冲突按记录展示并合并，不自动整库覆盖。在线账号与权限需要独立迁移；仅复制数据库不能消除 ChatGPT 登录依赖。

### 增长和备份

- 从整库 JSON 改为逐条写入、服务端分页与检索；读取列表时不载入全部原文和大附件。
- 附件与文本分离、内容哈希去重，保留来源引用；重复摘要不无限复制。
- 热记录与历史原文分开读取。暂不需要先部署复杂图数据库或专用向量数据库；出现检索质量或规模需求时再引入可重建索引。
- 方案建议：日增量、周完整备份、关键迁移前快照。保留至少一份用户自己的本地副本和一份不同位置的版本备份；备份恢复过程需实测。
- 备份必须涵盖个人空间、独立经验学习分支、全部附件、关系及规则/结构版本。数据库与附件清单使用一致快照，避免导出半批数据。
- 同步不能代替备份。避免误删或错误修改被同步到所有副本后无从恢复。
- 所有云端私人来源均保持私有权限；代码仓库保存程序和结构，私人正文与凭证不进入公开代码。

## 8. 实施顺序

A. 最小闭环：随手记收件箱、文本/截图/包导入、混合内容拆分、待办与观念视图、第一性原理分析模板、关联现有个人模型、完整可读导出。先用本截图作样本，保留日期未知。

B. 数据增长准备：备份 V3，建立按条 SQL 数据模型、附件对象存储、迁移校验和回滚路径。核验四大领域、个人模型、历史版本与独立学习分支；切换后只保留一个线上写入源。

C. 独立提醒与访问：接用户选定的日历或飞书提醒；完成状态闭环、送达/失败可查；迁入用户自有账号并实现独立登录，补离线阅读包。

D. 自动采集：WorkBuddy 固定输出协议、来源覆盖和幂等性跑通后，再做受限增量同步；长任务、自动外发、投递和不可逆操作仍需本人明确授权。

## 附录：给 WorkBuddy 的交接指令

请处理我主动转发给你的微信随手记录，并按“灵感一现”导入协议生成一批可追溯资料。

1. 先保留每条原消息、顺序、可见的作者和时间；时间缺失写 null，不推定为今天。截图保留原图，OCR 不确定处标记待核验。
2. 把混合记录拆为待办、观念、问题、目标/项目、学习线索；一条原消息允许对应多项，所有结果必须引用 source_ids。
3. 分开写原文、你的分析和候选行动。自己发出的消息可能是转贴 AI 或他人的话；来源不明标记 unknown，不能当作我的原创或已确认信念。
4. 对待办提取下一步动作、完成标准、日期和依赖。没有明确截止日期的 due_at 为 null；建议排期另存，不承诺已确认提醒。
5. 对值得展开的观念使用：现象→目标→事实与约束→假设→候选机制→替代解释/反例→验证行动。缺少信息就标记未知，不为每条简单待办写长分析。
6. 原文中的“学习卡神个人 agent”等未指明对象保留原词，标记需要补链接；不要擅自改成其他作者。
7. 输出 manifest.json、messages.jsonl、analysis.jsonl、attachments/、README.md，打包成 ZIP；无附件时也明确说明。仅在我指定的目录保存。
8. 保留原文，不修改微信历史；不访问未授权对话，不自动外发、不代为报名或投递，不使用知识库后台全权限凭证。
9. 若无法取得原文，只能处理总结，则标注 source_kind=secondary_summary，并说明缺失范围，不伪造原话、日期和真实行为。

本协议为目标格式，知识库的对应导入功能需要下一版实现；当前 V3 不能直接按此包自动导入。
