# 增量写入与冲突恢复

## 线上曾出现的现象

在网页里点「开始一次复盘」、选择记录、再保存时，页面顶部出现红底提示：

> 其他页面已更新这份资料。请先导出本页记录，再刷新合并，避免覆盖。

点「重试保存」仍然是同一句。看起来像任务无法完成，实际是写入被版本校验拦住了。

## 原因是三件事叠在一起

1. **整份覆盖式保存**：每次保存都提交整个 `workspace` 文档，服务端用 `If-Match: <ETag>` 做乐观锁。只要版本落后一次，整次保存就被拒。
2. **ETag 依赖边缘**：托管层会给响应改写自己的校验值（公开接口实测返回 `W/"..."` 弱校验，与后端 R2 对象的 etag 不是同一个字符串）。客户端一旦拿到被改写或缺失的 ETag，之后的每次写入都会对不上。
3. **重试不重新取版本**：旧版「重试保存」只是把同一份带旧 ETag 的请求再发一次，所以必然再次 409，形成死循环。

数据本身没有丢：被拒的写入没有落库，页面内存里还在；但用户看到的是「保存不了」，也就无法继续复盘。

## 现在的写入方式

```
POST /api/workspace/apply
{ "baseRevision": 12, "ops": [ { "collection": "records", "item": {...} }, ... ] }
```

- 客户端用 `workspaceOps(上次同步快照, 当前状态)` 只生成**真正变了的项**：同编号替换、新编号追加，没有任何删除操作。
- 服务端 `applyWorkspaceOps` 把操作合并到**当时最新的版本**上，再写回；写入被并发打断时自动重读重试，最多 5 次。
- 返回 `{status, revision, ops, attempts}`；客户端只认 `revision`，不再依赖 ETag。
- 保存失败时，待同步操作写入 `localStorage`，页面提示「重试同步」与「下载本页记录」，刷新后会自动再试一次。

保留的约束：

- 仍然只允许所有者账号或服务令牌写入，写操作要求同源。
- 仍然不允许删除历史：`apply` 只有 upsert，没有 delete；整份 `PUT` 仍需 `If-Match`，旧客户端不会误删。
- 合并后仍会跑 `validateState`，字段、编号、领域、数据量上限照旧校验。

## 能力边界（仍是长期风险）

- 线上现在仍是 V4 的旧写入路径；本仓库的 4.1.1 需要在 Sites 侧重新部署后才生效。
- 状态是 R2 上的单个 JSON 文档（约 2 MB 上限）。并发合并已经安全，但**规模**和**逐条审计**仍受单文档限制。
- `env.DB`（D1）目前只服务于随手记/收件箱子系统，工作台本体没有落到关系表。
- 没有服务端定时任务：复查提醒靠导出 ICS，不靠平台主动推送。
- 登录依赖 Sites 注入的身份头，没有独立账号体系；换域名或换托管需要重做鉴权。
